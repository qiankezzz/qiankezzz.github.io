PROJECT NOTES / 项目作品

Creator Toolbox.

一个在自己机器上运行的 AI 绘画作品管理与检索工具：把上千张本地出图整理成可检索的资产，并让元数据、角色与标签真正可用。

xte12329 · 2026.10

项目概览

Creator Toolbox 是一个本地部署的 AI 绘画作品管理工具，面向个人创作者，用于集中管理本地积累的 AI 生成图片（Stable Diffusion 与 ComfyUI 的输出），解决「图片越攒越多、找不到、理不清」的问题。我在项目中负责数据模型、后端接口、前端界面与部署链路的设计与实现。

它不做生成，只解决生成之后的事：把图片、参数、角色和标签组织成一个可以反复检索的私人图库。

问题与约束

AI 绘画的工作流会产生大量废稿与迭代稿：同一角色反复出图、参数散落在 PNG 元数据里、需要按角色或语义反复检索。通用相册工具无法理解 prompt、seed、LoRA、分区这些概念，而云端管理工具又要求把私人作品上传到别人的服务器。

因此项目一开始就定下三条硬约束：

  • 核心处理在本机完成——元数据解析、向量化、反向打标不依赖第三方云端图库服务。
  • 原图不降质——库内保存原图，另生成 WebP 派生图供浏览，减少传输体积。
  • 要能真实用起来——不是演示用的样品，需要应对上千张量级的图库。

我的工作

数据层。以 SQLite 存储图片元数据（正向与负向 prompt、模型、LoRA 链、采样器、seed、分区等），原图与派生的缩略图、预览图分目录存放；图片按内容哈希命名，重复导入自动识别并跳过。

元数据解析。解析 PNG 的 tEXt/iTXt 文本块，还原 ComfyUI 与 WebUI 两种工作流格式，把参数结构化后落库，而不是只当作一段文本保存。

图库浏览。瀑布流布局，支持按分区、来源、模型、标签、角色筛选与排序，以及批量收藏、改分区、加标签、删除；详情页支持在当前筛选结果内用方向键逐张翻阅，不需要反复返回列表。

语义搜索。集成 CLIP（clip-vit-base-patch32）为每张图计算图像向量，支持用自然语言描述来找图；向量写入数据库，检索时按余弦相似度排序。

角色归档。按「触发词 → 角色」的映射自动归档图片，并维护可持续扩展的角色卡。这里我做了取舍：不做模糊的语义归并，而是先用固定触发词精确匹配。因为对上万张图做全量语义聚类既慢又难以解释，而创作者其实很清楚自己要找的角色叫什么。

标签工作台。把 Danbooru 标签库（约 5 万条）按语义划分为推荐、外观、服饰、动作、表情、镜头、场景、光线、风格、角色/IP 等类别，附中文翻译，支持中英文双向查询，并可直接组装成 prompt 导出成文本。

批量反向打标。集成 WD14 Tagger 在本机做反向推理，从图片反推标签，结果同样按词库分类并配中文翻译，便于快速整理一批来源不明的图片。

部署。用单个 Node.js 进程同时承担前端静态托管与 API 反向代理，并加了一层访问密钥网关；对局域网提供 Caddy 的 HTTPS 入口，对外通过 Cloudflare Tunnel 暴露，后端只监听 127.0.0.1，不直接对外。

关键选择

一、离线环境下的模型加载。部署环境无法直连 HuggingFace。最初的表现是：每次导入图片都会「卡」很久，日志显示程序在反复尝试联网校验模型文件。当时的模型加载方式会触发联网请求，而加载异常不会被 lru_cache 缓存，于是每张图都要重试一遍并等待超时。

处理方式是：优先以 local_files_only=True 从本地缓存加载，失败才回退联网，并给加载失败加一段冷却期；同时在服务启动时后台预热模型与标签词库。改造后，模型加载不再落在用户操作的路径上。

二、导入性能：从「能跑」到「能连续用」。做性能剖析后发现，单张图片的导入耗时集中在两处：标签词库解析（对约 5 万个词条逐个跑 Python 循环，并反复拼接字符串）和派生图生成（同一张原图被完整解码两次）。

前者改为预编译正则——把分类词表合并成单条正则交给 C 层扫描、把敏感词拆成「单词集合 + 短语组」、用边界判断替代字符串拼接；后者改成一次解码共用，并对 JPEG 启用 draft，让解码器直接按比例降采样。再把「派生图生成」与「CLIP 向量化」这两件互不依赖的事放进线程池并行。

实测数据（13.4 MB 大图，本机直连后端，非公网链路）：

  • 词库解析：5.37s → 2.01s
  • 单张导入（服务刚重启后的首次）：约 9s → 2.88s
  • 稳态单张约 2.1s；3 张并行处理总耗时 2.62s

三、受限链路下的上传与下载。这是踩坑最多的部分。项目通过 Cloudflare Tunnel 对外，链路上有两道现实约束。

上传：我曾把前端改成 3 并发上传，结果在弱网下每张都被拖长，并出现 Cloudflare HTTP 524 超时；失败后重试又整包重传，进一步挤占带宽。改为串行上传后，总吞吐不变（受限于上行带宽），但每个请求都能更快结束，问题消失。后来我加了分段耗时日志，能一眼区分「链路慢」和「后端慢」——实测那条链路上传 6.9 MB 需要 123 秒，而服务端处理只用了 1.1 秒，说明瓶颈完全在链路上，此时继续优化后端已经没有意义。

下载：移动端点 <a download> 时，浏览器会把任务交接给系统下载器，并在十几毫秒内掐掉自己那条 HTTP/2 流，服务端数据没人读，TCP 接收窗口塌陷——表现为进度永远停在 0 B/s。改成页面内 fetch 读取后此问题消失，但新问题是对大文件会先把整包收进页面再落盘，下载管理器看不到，也无法按原方式管理下载。最终方案是按体积分流：超过 32 MB 交给浏览器原生下载，小文件继续走页面内读取以规避握手掐断。

验证与结果

  • 功能验证：主要模块均以真实图库跑通，导入 → 检索 → 打标 → 翻阅形成闭环。
  • 性能验证：上文数据均由日志与剖析输出复现，测试口径为本机直连后端。
  • 规模：写作时本地库为 1479 张图片、40 个角色。
  • 交付状态：自用运行中，尚未公开演示环境。

目前的局限也很明确：

  • 性能数据都是本机直连口径，公网访问受隧道带宽支配，不能直接套用。
  • 角色归档依赖触发词，未做语义聚类，冷门角色需要手工补触发词。
  • 单用户单机设计，没有并发用户、权限体系与自动备份机制。
  • 语义检索质量受限于 CLIP 对动漫内容的理解，长句描述的效果一般。

复盘

这个项目让我最深的体会是：性能问题要靠数据定位，而不是靠直觉。最初我以为导入慢是 AI 推理的锅，剖析之后才发现大头在标签词库解析和重复解码；后期加上分段日志后，又证明公网场景下瓶颈根本不在后端。

另一个体会是约束会改变最优解。并发在局域网是常识，在带宽受限的隧道上反而有害；<a download> 在桌面端是最省事的写法，在移动端却会直接坏事。同一个技术选择在不同链路上结论完全相反，所以必须先把链路测清楚再动手。

下一步打算：给角色归档加一层可解释的候选推荐，而不是全自动归并；把公网下载换成流式写盘，兼顾内存与进度；补上数据库备份与导出。
